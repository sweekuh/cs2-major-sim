# Milestone v1.0: Cologne 2026 Swiss-Stage Pick'Em (calibrated)

**Status:** ✅ SHIPPED 2026-05-30
**Phases:** 1-5
**Total Plans:** 14

## Overview

v1.0 is the calibrated Cologne 2026 Swiss-stage Pick'Em tool: a headless, backtest-validated
Valve Swiss engine, a generator-first Monte Carlo runner, a two-mode Streamlit UI, a dual-ballot
Pick'Em optimizer, conditional round-by-round re-simulation with live mode, and a fail-soft
three-provider market-odds ensemble. The build was one strict dependency chain — a faithful
Valve Swiss engine is worthless unless its pairing logic is provably correct, so the
round-by-round backtest was a **hard blocking gate** at the end of Phase 1. From there each
layer rode on the one below: the Streamlit shell (Phase 2) needs the generator-first MC and a
`locked`-keyed cache; the optimizer (Phase 3) needs the stored per-sim record sample; conditional
re-sim + live mode (Phase 4) needs the engine's `locked` support and the optimizer's P(≥5)
scoring; the odds ensemble (Phase 5) is a fail-soft enhancement that fills the epistemic outer
loop stubbed in Phase 1 and is placed last because rating-only mode is fully functional and the
first run needs no API key.

The milestone shipped with the GATE-01 Budapest 2025 backtest GREEN (the engine reproduces
StarLadder Budapest 2025 Stage 1's actual R1-R5 pairings EXACTLY), the full suite at 113 passed,
and all 54 v1.0 requirements satisfied. ~7,000 LOC Python (engine + ui + odds + scripts + app.py
+ tests) over 80 commits, 2026-05-28 → 2026-05-30.

## Phases

### Phase 1: Engine + Backtest Gate

**Goal**: A pytest-runnable, dependency-free correctness core that simulates the Valve Stage-1 Swiss format and reproduces a real past Major stage's pairings exactly — the hard gate that must pass before any output is trusted or any UI exists.
**Depends on**: Nothing (first phase)
**Plans**: 4 plans

Plans:

- [x] 01-01: Scaffold (uv, py>=3.12), full Wave 0 test harness, engine/probs.py math core, engine/teams.py seed→team fixtures + data/stage1.json (ENG-01/03, PROB-01..05, MC-06, GATE-02)
- [x] 01-02: engine/swiss.py — difficulty-ranked fold + verbatim priority-table oracle + rematch fallback + Bo3 placement + locked support + simulate_stage (ENG-02..08, GATE-03)
- [x] 01-03: engine/montecarlo.py generator-first MC (SeedSequence.spawn pinned chunks, Wilson bands, full sample retention, epistemic outer no-op) + `__main__` headless smoke run (ENG-09, MC-01..05, PROB-03/05)
- [x] 01-04: Budapest 2025 Stage 1 fixture transcribed + reconciled; full backtest later resolved GREEN (GATE-01/04) once authoritative Valve VRS-snapshot seeds were sourced

**Details:**
The phase ended in a named hard gate (`swiss-validated`, GATE-01..05). The round-by-round
backtest is the **only** check that proves greedy rematch resolution matches Valve's 15-row
priority table — invariant tests (Σ P = 2/8/2) pass even when Buchholz (ENG-03), the fold key
(ENG-04), or the priority table are wrong. The verbatim 15-row priority table was pulled from
`major-supplemental-rulebook.md`. Correctness-fatal facts locked in here: Buchholz =
`Σ(opp.wins − opp.losses)` not `Σ opp.wins`; fold sorts on difficulty-then-seed rank not raw
seed; `locked` support built from day one (needed by Phase 4); `SeedSequence.spawn` over pinned
chunks (DEFAULT_N_CHUNKS=20); MC generator-first with full per-sim record sample retained
(needed by Phases 2 and 3); epistemic outer loop stubbed as a single-draw no-op (filled in
Phase 5); odds-override math (PROB-02, Bo3 NOT re-applied) lives in probs.py from this phase.

At plan time GATE-01/04 were DEFERRED because the authoritative Valve seeds were unsourceable
(HLTV Cloudflare-walled) and VRS order did not reproduce R1/R2 pairings. The gate was resolved
GREEN on 2026-05-29: seeds were sourced from the authoritative Valve seeding VRS **snapshot**
(`ValveSoftware/counter-strike_regional_standings`, `invitation/2025/details/2025_11_03` — the
"snapshot rule", not live HLTV/VRS), and `test_backtest_budapest_2025` reproduces every round
R1-R5 exactly, including the 6-team R4/R5 priority-table groups (GATE-04 exercised against real
data, no fork needed). `BACKTEST_PASSED=True`.

### Phase 3: Pick'Em Optimizer

**Goal**: A decision layer that recommends both the E[correct]-optimal and P(≥5)-optimal ballots side by side, headlines the true P(≥5/10) coin odds, and warns on the correlated 0-3 trap — all scored against the stored per-sim sample, never a fresh MC run.
**Depends on**: Phase 1 (stored per-sim record sample), Phase 2 (UI to display ballots)
**Plans**: 2 plans

Plans:

- [x] 03-01: `engine/optimizer.py` pure core — Ballot A greedy (per-bucket marginal baseline), vectorized P(≥5) over `Result.sample`, E[correct], Ballot B hill-climb, correlated-0-3-in-R1 via `build_round1_pairs`, `optimize()` facade + tests (incl. `test_pge5_known_answer`) (OPT-01/02/04/05)
- [x] 03-02: UI wiring — fill `_hero_slot` with recommended-ballot P(≥5) (OPT-04), Ballot A vs B side by side with diff highlight (OPT-03), correlated-pick warning banner (OPT-05), `optimize_cached` memoized on the MC cache key + AppTest coverage

**Details:**
Ballot A = greedy (top 2 by P(3-0), top 2 by P(0-3), top 6 by P(advance) excluding the four
chosen); Ballot B = hill-climb single-team swaps + re-bucketing moves scored by P(≥5) against
the stored sample. Both valid exactly 2/6/2 with no team in two buckets, differing picks
highlighted. The chosen ballot's P(≥5/10) is computed by scoring each simulated stage's record
vector against it and shown as the hero number. A correlated-pick warning fires when the two 0-3
picks meet in Round 1; Ballot B automatically avoids the trap. The optimizer consumes the stored
sample and never re-runs the MC. Phase 3 V&V established (via brute-force counterexample) that
the bucket-wise greedy maximizes the per-bucket marginal sum, not global E[correct] — OPT-01 was
softened to "greedy per-bucket marginal baseline"; Ballot B (OPT-02) is the real P(≥5)
recommendation.

### Phase 4: Conditional Re-Sim + Live Mode

**Goal**: The killer feature — lock real results round by round, re-simulate conditioned on standings/Buchholz/rematch history, and show each locked pick as live/dead/secured with a P(≥5)-from-here delta, rendered over a record-bucket bracket.
**Depends on**: Phase 1 (engine `locked` support), Phase 2 (`locked` in cache key), Phase 3 (P(≥5) scoring reused for the from-here delta)
**Plans**: 2 plans

Plans:

- [x] 04-01: `engine/live.py` pure core (TDD) — lock-list↔`locked`-dict projection, `validate_lock` (rematch/terminated/non-pairing/double-booking/winner-not-in-pair reasons), `classify_pick` live/dead/secured, `pge5_delta` reusing `optimizer.p_ge5` on a fixed anchor ballot, `derive_bracket`/`legal_pairings_for_round` replaying `simulate_stage(..., pairings_out=[])` (RESIM-02/03/04)
- [x] 04-02: LIVE-mode UI wiring — round-by-round lock controls → `KEY_LOCKED` → existing `freeze_locked`→`cache_key` path (re-sim fires for free), from-here delta filling `_hero_slot`, per-pick status chips, record-bucket bracket (solid-locked/faint-simulated), `validate_lock` gating with `st.error` reason + AppTest (RESIM-01/02/03/04)

**Details:**
Locking a real round result fires a conditional re-sim automatically via the `locked` cache key;
locked winners are deterministic and at least one P(advance) value moves. Each locked pick
displays as live / dead / secured with a P(≥5)-from-here delta arrow (e.g. `71% → 58%`). An
impossible locked pairing (rematch or already-terminated team) is rejected with a reason, not
silently accepted. The bracket renders as record-bucket columns (HLTV/Liquipedia convention,
never a tree) with locked/real results solid and simulated branches faint. Re-sim fires "for
free" because `locked` was already in the cache key from Phase 2 and honored by swiss.py from
Phase 1 — no engine mutation.

### Phase 5: Odds Ensemble

**Goal**: Live multi-provider market odds blended into honestly-banded probabilities and back-solved into per-team ratings — a fail-soft enhancement that never crashes, never gates, and writes a read-only cache the app only reads.
**Depends on**: Phases 1–4 (engine, UI, optimizer, re-sim all proven; epistemic outer loop stubbed in Phase 1)
**Plans**: 3 plans

Plans:

- [x] 05-01: pure `odds/` core (TDD) — `OddsProvider` adapters (OddsPapi/Polymarket/Kalshi over recorded fixtures), de-vig routed on `vig_type`, OddsPapi bundle pre-pooled to one Pinnacle opinion, liquidity/sharpness-weighted log-opinion `pool()` → `BlendedProb(p,var,n_sources)`. httpx confined to `odds/` (ODDS-01/02/03/05)
- [x] 05-02: `engine/backsolve.py` (TDD) — invert series→map (Bo1 identity, bisection-invert `p²(3−2p)`) + numpy-only Gauss-Newton logistic rating fit (no scipy); fill `epistemic_draws` with K Beta draws (k=1+var=0 = byte-identical no-op); additive keyword-only `market_overrides` threaded `simulate_stage`→`_play`. Band ⊇ Wilson, N-stable (ODDS-04/PROB-03/04/05)
- [x] 05-03: fetch + cache + UI — `scripts/fetch_odds.py` (button AND v2 cron) writing read-only `data/odds_cache.json`; `ui/odds_loader.py` json-only read path; "fetch now" button + fail-soft preservation (no key → rating-only + banner, zero-config first run intact); app never calls providers on rerun (ODDS-05/06/07/08)

**Details:**
With provider keys present, a "fetch now" button pulls OddsPapi (Pinnacle anchor) + Polymarket +
Kalshi, normalizes per source (de-vig fixed-odds, spread/fee-only for prediction markets), and
log-opinion-pools them weighted by originate/liquidity into a blended p + cross-source variance.
With NO key, the app runs rating-only with a one-line info banner and never crashes — the
zero-config first run from Phase 2 still works. Ratings back-solve inverts each known series prob
to map-level (identity Bo1, invert `p²(3−2p)` for Bo3) then fits per-team ratings via logistic
least-squares; live odds override the imminent round's known matchups. The epistemic outer loop
draws p ~ Beta(blend, clamped var) with `variance < p(1-p)` clamp before the moment fit; the
reported band ⊇ the inner Wilson band and does NOT shrink with N on high-disagreement matches.
The fetch writes a read-only `data/odds_cache.json` the app only ever reads; the app never calls
`get_quotes()` on a rerun (httpx/dotenv verified OUT of the app import path). The v2 cron
(OPS-01, deferred) is a drop-in: the same `scripts/fetch_odds.py`, the same cache contract, zero
app changes. The live slug/ticker confirm is a DEFERRED `/browse` checkpoint — recorded
OUTSTANDING because Cologne markets had not posted by 2026-05-30; `discover_fixtures()` returns
`{}` by design and is a one-function fill once the bracket posts.

## Milestone Summary

**Key Decisions:**

- Decision: Buchholz / Difficulty Score = `Σ(opp.wins − opp.losses)`, single seeding code path (Rationale: verified against the rulebook worked example; `Σ opp.wins` passes invariants but silently corrupts every probability) — ✓ Good
- Decision: Bo3 = closed form `p²(3−2p)` as a single Bernoulli draw, never sample 3 maps (Rationale: exact for iid maps; sampling 3 maps only adds cost + MC noise) — ✓ Good
- Decision: Epistemic (source-disagreement) variance as an OUTER loop, never folded into per-sim sampling; clamp `variance < p(1−p)` before the Beta fit (Rationale: keeps source disagreement out of aleatoric noise so the Wilson band isn't falsely tight at large N, and the fit doesn't crash on thin-liquidity matches) — ✓ Good
- Decision: The round-by-round backtest is a slice-1 hard gate, not post-hoc validation (Rationale: the only check that proves greedy rematch resolution matches Valve's 15-row priority table; invariant tests pass even when the engine is wrong) — ✓ Good
- Decision: Odds v1 = all three providers live (Pinnacle/OddsPapi + Polymarket + Kalshi), fail-soft (Rationale: user wants the divergence signal up front; missing key → rating-only mode, never a crash or a gate) — ✓ Good
- Decision: Interface = Streamlit (not static HTML) (Rationale: same process as engine + odds layer; only option that can run keyed server-side odds calls) — ✓ Good

**Issues Resolved:**

- GATE-01/04/05 backtest went GREEN 2026-05-29 — the original blocker (no authoritative seed source; HLTV Cloudflare-walled, VRS order failed R1/R2) was resolved by adopting the Valve VRS **snapshot** rule (`counter-strike_regional_standings` 2025_11_03). `test_backtest_budapest_2025` reproduces Budapest 2025 Stage 1 R1-R5 exactly, including the 6-team R4/R5 priority-table groups. `BACKTEST_PASSED=True`.
- Phase 3 V&V greedy-optimality caveat resolved by softening OPT-01 to "greedy per-bucket marginal baseline" and broadening Ballot B's hill-climb with re-bucketing moves.
