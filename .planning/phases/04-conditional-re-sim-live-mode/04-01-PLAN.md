<objective>
Build `engine/live.py` — the pure live-mode core that sits on top of the FROZEN engine and
optimizer. It owns four streamlit-free, RNG-deterministic functions the Plan-02 UI wires in:
the lock-list ↔ `locked`-dict projection (D1), `validate_lock` rejecting every impossible
pairing with the exact reason string (D3/RESIM-03), `classify_pick` mapping a (team, bucket)
pick to live/dead/secured against the CONDITIONAL sample (D4/RESIM-02), `pge5_delta` computing
the from-here arrow as two `p_ge5` calls on a FIXED anchor ballot (D5/RESIM-02), and
`derive_bracket` replaying `simulate_stage` with the partial `locked` to yield both the
validator's per-round `legal_pairings` and the record-bucket standings (D6/RESIM-04).

The load-bearing discovery (RESEARCH): the engine ALREADY answers Phase 4's two hardest
questions — "which pairings exist at round R?" and "what is the record-bucket layout?" — by
replaying `simulate_stage(..., pairings_out=[])` with the current locks. This plan never
re-derives pairings by hand (that would re-open the GATE-01 seed/Buchholz blind spot); it asks
the proven engine. **No engine mutation:** `engine/live.py` imports swiss/optimizer/teams and
calls them; the Budapest backtest stays green.

**The rng-invariance invariant (BLOCKER fix):** `simulate_stage` computes each round's pairings
from the START-OF-ROUND standings (swiss.py:281-296), so round R's pairings depend on who WON
the unlocked games of rounds < R. That means `pairings_out[round_idx]` is a deterministic,
format-determined set ONLY when every prior round is fully locked; with an incomplete prefix it
is a single-RNG-draw artifact and the validator's `legal_pairings` would accept/reject legal
locks based on one arbitrary draw. The live-mode invariant already forbids this — round R only
opens once R-1 is fully entered — so `legal_pairings_for_round` REQUIRES a fully-locked prefix
and raises `LivePrefixIncomplete` otherwise (never returns a draw artifact). `derive_bracket`
(read-only standings/render) tolerates a partial prefix; only the validator-feeding
`legal_pairings_for_round` enforces the precondition.

Purpose: after this plan the entire live-mode decision math is provable in `pytest` with no UI
— mirroring the Phase 1/3 discipline (correctness core first, then the shell). Authored TDD
(RED test task → GREEN impl tasks) even though global tdd_mode is off, because Phase 1 and
Phase 3 cores were authored TDD-first and the criticals here (`test_classify_secured_dead_live`,
`test_derive_bracket_pairings_match_engine`, `test_legal_pairings_requires_full_prefix`) demand it.

Output: `engine/live.py` and `tests/test_live.py`.
