<objective>
Wire the Plan-01 live core into the Phase-2 LIVE-mode shell that `app.py` already stubs
(the research cites the exact stub locations: `_hero_slot`, the "Your picks — status" block,
the status legend, the "Delta probabilities" subheader, and `_render_bracket`). This plan
fills those stubs so a user can lock results round-by-round and watch the stage re-sim from
here. Five wiring jobs:

1. **Lock controls** (D1/D2/RESIM-01) — round-by-round winner pickers writing
   `st.session_state[KEY_LOCKED]` (a new `KEY_LOCKED = "locked_results"` list + pure lock-list
   helpers in `ui/state.py`); derive the engine `locked` dict and feed it through the EXISTING
   `freeze_locked` → `locked_key` → `cache_key` path in `_run_or_serve` (the `locked: dict = {}`
   line at `app.py:305` is the single fill point). Re-sim fires for free. Round-R controls appear
   ONLY once round R-1 is fully entered (the live-mode invariant — so
   `legal_pairings_for_round` is only ever called on a fully-locked prefix and never raises
   `LivePrefixIncomplete`).
2. **From-here delta hero** (D5/RESIM-02) — fill the LIVE `_hero_slot` with `before% → after%`
   via `hero_number_html`, anchored on the recommended ballot (Ballot B) captured at the FIRST
   Run from the EMPTY-locked Result and held fixed across locks.
3. **Per-pick status chips** (D4/RESIM-02) — classify each picked (team, bucket) via
   `engine.live.classify_pick` and render with the existing `status_badge_html`
   (blue/amber + glyph + label, never red/green).
4. **Record-bucket bracket** (D6/RESIM-04) — replace `_render_bracket` with columns from
   `engine.live.derive_bracket`: solid locked / faint simulated chips, `html.escape` names,
   NEVER a tree.
5. **Lock gating** (D3/RESIM-03) — run `engine.live.validate_lock` before committing; on a
   reason, show `st.error`, block the lock, and do NOT mutate `KEY_LOCKED` or the cache.

**How the real `_run_or_serve` works (BLOCKER 1 — code-real anchor/pre-lock flow):**
`_run_or_serve` does NOT use `run_mc_cached`/`@st.cache_data`. It computes via `_drive_progress`
(a progress-bar generator over `run_mc_progressive`) and stores the Result into the SESSION
`mc_cache` dict (`st.session_state[KEY_MC_CACHE]`) keyed on `(ratings_key, S, int(N),
locked_key)`. The post-lock `result` it returns is the CONDITIONAL Result. The delta therefore
needs a SEPARATE pre-lock anchor: the EMPTY-locked Result. Derive its key explicitly as
`pre_key = (ratings_key, S, int(N), freeze_locked({}))`. Serve `pre_lock_result` from
`mc_cache[pre_key]` if present (the user's first pre-stage Run already populated it); else
produce it via ONE explicit compute on `pre_key` and memoize it into `mc_cache[pre_key]` — see
the chosen mechanism in Task 2's `<action>`. Capture the anchor as
`optimize_cached(pre_lock_result, *pre_key).recommended` — the pre-lock Result paired with its
OWN key, NOT the post-lock `result` with a mismatched key.

Purpose: a user can now do something genuinely new — lock real Cologne results as they happen
and see their own ballot's odds move, with impossible inputs rejected and the bracket reading
the way HLTV/Liquipedia show it. This is "the killer feature" (ROADMAP Phase 4 goal).

Output: `ui/state.py` (KEY_LOCKED + lock helpers), `ui/render.py` (`bracket_columns_html`),
`app.py` (lock controls + delta hero + status chips + bracket + lock gating), and AppTest
coverage in `tests/test_app.py`.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| user lock pickers → validate_lock | Untrusted (winner,loser,round) from the UI; validated by engine.live.validate_lock BEFORE any commit/engine call (RESIM-03) |
| KEY_LOCKED → freeze_locked → cache_key | Derived locked dict flows through the proven hashable cache key (Pitfall 13 — locked is a REAL key arg) |
| derive_bracket/classify output → st.markdown(unsafe_allow_html=True) | App-generated HTML from team names (html.escape-d via name_of) + STATUS glyphs only; no user free-text |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-04-STALE | Tampering | stale pre-lock distributions in Live (Pitfall 13) | mitigate | locked dict derived from KEY_LOCKED flows through freeze_locked->locked_key (a REAL cache-key arg, ui/cache.py); test_live_lock_changes_cache_key + test_live_lock_moves_p_advance assert detection |
| T-04-XSS | Tampering | bracket_columns_html via unsafe_allow_html | mitigate | team names html.escape-d via name_of (like _ballot_card_html); STATUS glyphs are fixed in-code literals; numbers via fmt_pct/hero_number_html only |
| T-04-BADLOCK | Spoofing/Validation | impossible lock silently accepted | mitigate | validate_lock runs before commit; st.error shows the reason, KEY_LOCKED + mc_cache unchanged (test_impossible_lock_shows_reason) |
| T-04-ANCHOR | Repudiation | delta re-optimizing the ballot per round (arrow meaningless) OR anchored on the wrong (post-lock) Result/key | mitigate | anchor ballot (Ballot B) captured once from the EMPTY-locked pre_key Result via optimize_cached(pre_lock_result,*pre_key).recommended, stored in session_state KEY_LIVE_ANCHOR; pge5_delta uses the SAME fixed ballot + the pre_key Result for before (test_live_delta_anchor_uses_pre_key) |
| T-04-PREFIX | Validation | legal_pairings_for_round called on an incomplete prefix (raises / arbitrary draw) | mitigate | round-R controls render only once R-1 is fully entered; legal_pairings_for_round is never called on a partial prefix |
| T-04-TREE | (UI correctness) | bracket drawn as a tree | mitigate | bracket_columns_html emits record-bucket flex columns only; test asserts columns not a tree (RESIM-04) |
| T-04-COLOR | (UI accessibility) | status chip drift to red/green | mitigate | reuse status_badge_html / STATUS verbatim — blue/amber + glyph + label (UI-06) |
</threat_model>
